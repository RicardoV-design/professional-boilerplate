# API Boilerplate Project (with Authentication)

## Project Description

A production-ready backend boilerplate built with Node.js, Express, TypeScript, and TypeORM. This template is designed to streamline the development of scalable RESTful APIs. It features strict request validation, centralized error management, structured logging, database migration workflows, and is now fully upgraded with a secure, stateless JSON Web Token (JWT) authentication system and Role-Based Access Control (RBAC) architecture.

## Authentication Flow Documentation

1. **Authentication:** The client sends valid credentials (e.g., email and password) to the server.
2. **Token Issuance:** The server verifies the password using bcrypt, generates a stateless JWT containing the user's ID and role, and returns it to the client.
3. **Transmission:** The client stores this token and includes it in the HTTP headers of all subsequent requests.
4. **Authorization:** The server's authentication middleware intercepts incoming requests, mathematically verifies the JWT signature, and grants or denies access based on the token's validity and the user's embedded role.

### How to Get a Token (Login Endpoint)

To retrieve an access token, make a `POST` request to the login endpoint with your credentials.

**Endpoint:** `POST /api/auth/login`

**Payload (JSON):**
```json
{
    "email": "user@example.com",
    "password": "your_secure_password"
}
```

### Endpoints Overview

**Public Endpoints (No Token Required):**
* `GET /health` - Server health check.
* `POST /api/auth/login` - Authenticate and retrieve a JWT.
* `POST /api/users` - Register a new user account.

**Protected Endpoints (Requires Valid Token):**
* `GET /api/auth/me` - Retrieve the currently authenticated user's profile.
* `PUT /api/users/:id` - Update an existing user's information.

**Restricted Endpoints (Requires Valid Token + Admin Role):**
* `GET /api/users` - Retrieve a paginated list of all users.
* `DELETE /api/users/:id` - Delete a user account.

## Project Reflection 

**1. What is the difference between authentication and authorization? Give a real-world example of each.**
> Authentication is verifying the identity of an account while authorization is being authorized to login but if has the permission to access certain stuffs. Like the PC on our school (BC) on computer laboratory wherein has a Standard User but restricted as not authorized to do major changes on it. 

**2. Why is JWT considered "stateless" and how does that benefit scalability?**
> JSON Web Tokens (JWTs) are considered stateless because the server does not need to store session records in a database or server memory to verify a user's identity. Instead, all necessary authentication data (such as user IDs, roles, and expiration timestamps) is cryptographically signed and embedded directly within the token payload itself.

**3. What are the three parts of a JWT token and what does each part do?**
> It's the header, payload and signature.   
> * **Header** - This section contains the configuration metadata for the token. It usually consists of 2 properties: *the type of the token (which is explicitly set to JWT)* and the *cryptographic signing algorithm.*   
> * **Payload** - This is the actual data package containing the "claims," which are readable statements about the user.   
> * **Signature** - This secure validation string is generated by taking the encoded header, the encoded payload, a private secret key known only to your server, and running them through the hashing algorithm specified in the header.  

**4. Why should you never put sensitive data (like passwords) in the JWT payload?**
> Because the JWT payload is merely Base64Url encoded, not encrypted. It can easily be decoded and prone to be compromised. 

**5. How does bcrypt protect user passwords? What is the purpose of the "salt" and "rounds"?**
> Bcrypt protects user passwords by transforming them into irreversible hashes, ensuring that even if a database is compromised, the original plaintext passwords cannot be read or recovered by an attacker.
> * **Salt** - Randomly generated string automatically appended to the plaintext password before the hashing process begins.
> * **Rounds** - The "rounds" parameter defines the computational cost of the hash by dictating how many iterations the algorithm must execute. 

**6. What happens if someone steals a JWT token? How can you mitigate this risk?**
> If a JWT is stolen, the attacker can fully impersonate the user and execute any actions or access any protected API endpoints. It indicates can bypass login processes. It can be mitigated by short expiration times, refresh token rotation and secure client storage. 

**7. Why is it important to use HTTPS when transmitting JWT tokens?**
> It is important to use HTTPS when transmitting JWT tokens because it encrypts the entire communication channel between the client and the server, protecting the token from being intercepted in transit.

**8. What is the difference between a short-lived access token and a long-lived refresh token? When would you use each?**
> Short-lived access token is a stateless credential used to directly authorize frequent API requests, while a long-lived refresh token is a highly secure, stateful credential used exclusively to obtain new access tokens without requiring the user to re-enter their credentials.

**9. How does the auth middleware know which user is making the request?**
> The auth middleware identifies the user through a sequential process that extracts, verifies, and decodes the JSON Web Token.

**10. If you had to implement role-based authorization (e.g., admin vs. regular user), how would you modify your current setup?**
> With this, I prefer implementing role-based authorization on admin. 
>
> **Update the User Entity** (`src/entities/User.ts`)
> ```typescript
> @Column({ type: 'varchar', default: 'user' })
> role: string; // Typically 'user' or 'admin'
> ```
>
> **Inject the Role into the JWT Payload** (`src/services/authService.ts`)
> ```typescript
> const payload: TokenPayload = { 
>     userId: user.id, 
>     role: user.role 
> };
> const token = jwt.sign(payload, config.jwt.secret, { expiresIn: '15m' });
> ```
>
> **Create the Admin Middleware** (`src/middleware/roleAuth.ts`)
> ```typescript
> import { Request, Response, NextFunction } from 'express';
> import { ForbiddenError } from '../utils/errors';
>
> export const requireAdmin = (req: Request, res: Response, next: NextFunction) => {
>     // req.user is populated by your previous requireAuth middleware
>     if (!req.user) {
>         return next(new ForbiddenError('User not authenticated'));
>     }
>
>     if (req.user.role !== 'admin') {
>         return next(new ForbiddenError('Administrator privileges required'));
>     }
>
>     next();
> };
> ```
>
> **Middleware on Protected Routes** (`src/routes/userRoutes.ts`)
> ```typescript
> import { requireAdmin } from '../middleware/roleAuth';
>
> // ONLY an admin can delete users
> router.delete('/:id', requireAuth, requireAdmin, userController.deleteUser);
> ```
